# Excel 分页、证据与超时恢复修复

## 已核实的故障

用户提供的蒸发器会话在发布前完成了多次读取，但旧校验要求单次读取完整包含理解范围。
`A1:N19`、`A20:N47`、`A48:N74` 的并集完整覆盖 `A1:N74`，旧实现仍拒绝发布。
同时旧分页只限制单元格部分，附带原文和元数据后超出 DSH 的 50000 字节内联上限。
原生日志中的两页结果分别被省略 6234、4151 字节，返回体含 spill 提示，不能作为完整 JSON 读取。

该轮在启动后 175.974 秒发布失败，175.981 秒进入下一步，180.021 秒被旧整轮超时释放。
因此日志中的末尾 502 不能据此认定为网络故障。重复正文是累计文字快照，heartbeat 是 SSE 保活。
预览不可用是另一个条件：当时 Windows 启动环境未设置 `EXCEL_RENDER_WSL`。

## 实现

- `read-page.js` / `ranges.js`：整个读取响应按 32000 个 UTF-8 字节分页，包括值、原文、元数据、文件及会话引用。返回 `returnedRange` 和全部 `nextRanges`；超大单格明确报错且不确认已读。
- `read-receipts.js`：根据原生日志中完整新版工具结果确认已读；执行函数返回不等于送达。截断结果、旧记录和其他会话不计入确认。按 Agent 增量消费事件，避免每次重扫全部历史。
- `read-coverage.js`：矩形并集严格减去已读区域，保留真实缺口；返回 `EXCEL_COVERAGE_INCOMPLETE` 和待补读坐标。
- `understanding.js`：引用错误返回 `EXCEL_QUOTE_MISMATCH`、条目路径和坐标，有限长度内附精确原文。保持原始值和规范化校验，不放宽来源要求。
- `turn-budget.js`：整轮默认十分钟，无新进展默认三分钟。仅当前 Agent 的模型、工具、步骤事件刷新无进展计时；心跳不刷新。HTTP / SSE 区分两类 504，并保留会话 ID。
- 旧读取记录保留在原状态文件，仅带 `version: 2` 的完整送达记录参与新结果校验；原件、索引和旧结果无需迁移或重新上传。

## 真实蒸发器文件

使用本地已上传的 `4-蒸发器客户输入.xls`，129536 字节，SHA-256：
`58e88eb29eb14a11dbb5b6062cb61aadbb099a88e5c393828ffb52ece44988a8`。
测试只读取原件，在独立临时会话上传副本；客户文件没有加入源码或分发包。

真实 Cordis 工具循环通过 6 个完整响应覆盖 `Heat Pump Inputs!A1:N74`。
密集合成表需 18 页；发送给供应商的每页均为合法 JSON，至多 32000 字节，没有宿主省略内容。
两种表均故意先声明未读范围，再补读，接着制造不匹配的整表引用，按错误修正后成功发布并验证重启恢复。
字段检查包含 `D33` 原始数值 10、显示文本 `10.0`，以及单位来源 `B33` 的 `psid`。

原失败的 62 字段候选也做了只读离线回放。字段原值、原文与来源都通过结构校验；两个其他引用有问题：

- `observations[0]` 把整表坐标与标题文字搭配。
- `issues[4].evidence[0]` 存在同样不匹配。

仅在内存中去掉无预览支撑的观察，并保留不附单元格证据的“预览不可用”问题后，完整候选通过程序校验。
没有替用户修改或发布原会话结果；这也不代表 62 字段的业务解释和单位候选都已人工确认。
证据 `.dsh/excel-fix-original-replay.json` 记录最大页 31948 字节和原状态文件未改变。

## 使用与边界

重启项目启动脚本以加载新代码，重新打开原对话后要求继续读取和发布即可。
旧附件原件仍在；Agent 应按新版工具补读，再依据精确错误修正引用。没有停止或重启用户正在运行的服务。
Windows 如需预览，启动进程需继承 `EXCEL_RENDER_WSL=Ubuntu`；WSL 内渲染依赖及真实图片传输已测试。
本次运行没有重新执行浏览器操作，也未实测外部模型对修正提示的遵循度；原交付的浏览器证据见同目录 Excel 插件验收记录。
全量真实客户表人工标注、冷凝器字段准确率和正式参数映射仍在原任务的待验范围内。
保留工作区原有改动，未 commit、push 或修改用户会话产物。
